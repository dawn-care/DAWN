## Basics

### Base URL

Every path in this guide is relative to the API base URL both apps already use, which ends in `/api`:

| App | Setting | Local value |
|---|---|---|
| Caregiver (Vite) | `import.meta.env.VITE_API_URL` | `http://localhost:8080/api` |
| Tablet (Expo) | `API_URL` from `carepartner/src/api/config.ts` | `http://localhost:8080/api`, or `http://10.0.2.2:8080/api` on the Android emulator |

So `GET /screen` means `${API_URL}/screen`.

### Media URLs

Responses never contain storage paths. Anything with a file has a `url` such as `"/media/4/file"`, relative to the same base. Join it to the base to use it:

```tsx
<img src={`${API_URL}${photo.url}`} />                 // caregiver
<Image source={{ uri: resolveApiUri(photo.url) }} />   // tablet, existing helper
```

File URLs support HTTP Range requests, so video and audio players can seek.

### Which carepartner

Nothing here is behind a login yet. Requests name the carepartner with `carepartner_id`, either in the query string or the body. The caregiver app uses `activeCarePartnerId` from `AuthContext`; the tablet uses the paired ID from `getCarepartnerId()`. Endpoints that take an item ID (`/media/{id}`, `/screen-widgets/{id}`, `/scheduled-items/{id}`) work out the carepartner from the item.

### Dates and times

Dates are `"YYYY-MM-DD"` and times are `"HH:MM"` (24 hour), always in the carepartner's local time. Send them exactly as the caregiver picked them; never convert to UTC. The carepartner's timezone (default `America/New_York`) is on the carepartner record and in the `/screen` response.

### Errors

Every new endpoint returns errors as JSON with a stable `code` to switch on and an English `error` for logs:

```http
HTTP/1.1 400 Bad Request

{ "code": "NOT_ON_15_MIN_STEP", "error": "start_time must be on a 15 minute step (:00, :15, :30 or :45)" }
```

Show your own wording to caregivers, keyed by `code`; the full list is in [Error codes](#error-codes). Successful deletes return `204` with no body.

### Browsing and testing

- Swagger UI with every endpoint and schema: `http://localhost:8080/swagger/index.html` (generated by the Docker build).
- An example `/screen` response for the Balanced layout is in [The tablet screen](#the-tablet-screen).
- Allowed browser origins (CORS): `http://localhost:5173`, `http://localhost:8081` and the production domain. Methods include `PATCH`.

## Fetch helper and types

A small wrapper turns error responses into exceptions that carry the code. Copy it into each app's API layer and change only how `API_URL` is read.

```ts
const API_URL = import.meta.env.VITE_API_URL; // tablet: import { API_URL } from "./config"

export class ApiError extends Error {
  constructor(public status: number, public code: string, message: string) {
    super(message);
  }
}

export async function api<T>(path: string, init: RequestInit = {}): Promise<T> {
  const headers = init.body && !(init.body instanceof FormData)
    ? { "Content-Type": "application/json", ...init.headers }
    : init.headers;
  const res = await fetch(`${API_URL}${path}`, { ...init, headers });
  if (res.status === 204) return undefined as T;
  const body = await res.json().catch(() => null);
  if (!res.ok) {
    throw new ApiError(res.status, body?.code ?? "INTERNAL_ERROR", body?.error ?? res.statusText);
  }
  return body as T;
}

// Example
const settings = await api<ScreenSettings>(`/screen-settings?carepartner_id=${id}`);
```

## Media library

One library for photos, videos and audio. The server measures video and audio length itself on upload.

### `POST /media`

Upload a file as `multipart/form-data`. Returns `201` with the new `Media`.

| Field | |
|---|---|
| `file` | the file |
| `kind` | `photo`, `video` or `audio` |
| `carepartner_id` | |
| `display_name` | optional; defaults to the file name without its extension |

Video and audio over 10 minutes are rejected with `MEDIA_TOO_LONG`. Files over 1 GB get `FILE_TOO_LARGE`. Accepted types: photos JPEG, PNG, GIF, WebP, HEIC; videos MP4, MOV, WebM, Ogg; audio MP3, WAV, M4A, Ogg, WebM.

```ts
const form = new FormData();
form.append("file", file);              // from <input type="file">
form.append("kind", "photo");
form.append("carepartner_id", String(carepartnerId));
const media = await api<Media>("/media", { method: "POST", body: form });
// Don't set Content-Type yourself; the browser adds the multipart boundary.
```

### `GET /media?carepartner_id={id}&kind={kind}`

List a carepartner's media, newest first. `kind` is optional. Use `usage` for the library badges: photos can be `on_screen`, `audio_background` and `scheduled` at once; video and audio can only be `scheduled`. An empty list means saved but unused.

### `GET /media/{id}`

One item, with the same fields as the list.

### `GET /media/{id}/file`

The file itself, with its real `Content-Type`. This is what `url` points to.

### `PATCH /media/{id}`

Rename. Body `{"display_name": "Beach day"}`, 1 to 200 characters. The file doesn't move.

### `DELETE /media/{id}`

Delete the item and its file. What else changes, so the confirmation can say so:

- **Photo:** photo widgets showing it are removed; message widgets and audio items that used it lose the photo but stay; timed-photo scheduled items that show it are removed.
- **Video or audio:** every scheduled item that plays it is removed.

Check `usage` first and warn when it isn't empty.

## Screen settings and presets

Every carepartner gets settings when they're created: the Balanced layout, awake from 07:00 to 21:00. `layout_preset` is one of the names from `/screen-settings/presets`.

### `GET /screen-settings?carepartner_id={id}`

Returns `ScreenSettings`.

### `PUT /screen-settings?carepartner_id={id}`

Replace all three settings; every field is required. Wake time must be 06:00 to 10:00 and bed time 19:00 to 22:00, inclusive. `"6:30"` is accepted and stored as `"06:30"`.

```json
{ "layout_preset": "balanced", "wake_time": "07:00", "bed_time": "21:00" }
```

### `GET /screen-settings/presets`

Every layout and how many widget spots it has. Take the list of layouts and their spot counts from here instead of hard-coding them.

```json
[
  { "name": "simple",   "spots": 2 },
  { "name": "balanced", "spots": 4 },
  { "name": "grid",     "spots": 4 },
  { "name": "busier",   "spots": 6 }
]
```

The server only knows how many spots each layout has. Where each spot sits on screen is up to the frontend and the tablet. Spot numbers mean the same thing in every layout, so a widget keeps its place when the caregiver switches layouts.

## Screen widgets

The caregiver fills the current layout spot by spot. Each widget has a 0-based `spot`, and **any widget type can go in any spot**. A new carepartner has no widgets.

A widget whose `spot` is past the current layout's last spot is kept but hidden. For example, after switching from Busier (6 spots) to Simple (2 spots), widgets in spots 2 to 5 are hidden. They come back in the same spots when the caregiver switches to a layout with enough spots.

### `GET /screen-widgets?carepartner_id={id}`

All widgets in spot order, so hidden widgets (`hidden: true`) come last. Show them separately in the editor ("2 widgets don't fit this layout").

### `POST /screen-widgets`

Place a widget in an empty spot of the current layout. Returns `201` with the `ScreenWidget`. A spot the layout doesn't have gets `UNKNOWN_SPOT`; a spot that already has a widget gets `SPOT_TAKEN`.

```json
{ "carepartner_id": 1, "type": "photo", "spot": 0,
  "config": { "caption": "Sarah" }, "photo_media_id": 4 }
```

```json
{ "carepartner_id": 1, "type": "weather", "spot": 2, "config": { "zip": "14617" } }
```

```json
{
  "id": 10, "carepartner_id": 1, "type": "weather", "spot": 2,
  "config": { "zip": "14617" }, "photo_media_id": null, "photo_url": null, "hidden": false
}
```

### `GET /screen-widgets/{id}`

One widget.

### `PUT /screen-widgets/{id}`

Replace a widget's settings and photo: `{"config": {...}, "photo_media_id": 4}`. Send the whole config, not just the changed field. Its type and spot don't change.

### `POST /screen-widgets/{id}/move`

Move to another spot: `{"spot": 2}`. The spot must exist in the current layout (`UNKNOWN_SPOT` otherwise). If it has a widget, the two always swap places. Use this for drag and drop.

Moving a hidden widget into view sends the widget that was there to the hidden widget's old spot, so that one becomes hidden instead.

### `DELETE /screen-widgets/{id}`

Remove a widget; its spot becomes empty.

### Widget settings by type

Unknown fields are rejected (`INVALID_CONFIG`), which catches typos. Text is trimmed.

Every type can go in any spot.

| Type | `config` | Photo |
|---|---|---|
| `photo` | `caption` optional, up to 60 characters. Without it the screen shows the photo's name. | Required |
| `message` | `text` required (200). Optional `location` (100), `about` (`caregiver` or `carepartner`, for location reassurance), `label` (40) such as "Nurse". | Optional |
| `reminder` | `items`: 1 to 10 of `{time, text, icon}`. `text` up to 60. Icons: `meal`, `medication`, `walk`, `visit`, `appointment`, `call`, `rest`, `other` (the default). Items come back sorted by time. | None |
| `weather` | `zip`: 5 digit US zip. Defaults to `14617` (St. Ann's) when left out. | None |
| `sports` | `league` (`nfl`, `nba`, `mlb`, `nhl`) and `team`, an abbreviation from [the teams list](#sports-teams). | None |
| `news` | No settings: send `{}`. | None |

Photos must be `kind: "photo"` and belong to the same carepartner (`INVALID_PHOTO` otherwise).

## Sports teams

### `GET /widgets/sports/teams?league={league}`

The leagues and teams a sports widget can follow; `league` is optional. This replaces the hardcoded `SPORTS_TEAMS` list in `caregiver/src/pages/WidgetForm.tsx`. Store the `abbr` in the widget's config.

```json
[{ "id": "mlb", "name": "MLB", "teams": [{ "name": "New York Yankees", "abbr": "NYY" }] }]
```

(The real response lists all four leagues and every team.)

## Scheduled items

Things that play at a set time, once or on repeat. There are four shapes; the server works the shape out from the media and rejects anything else with `INVALID_SHAPE`.

| Shape | `media_id` | `background_photo_id` | `display_seconds` |
|---|---|---|---|
| `video` | a video | none | none |
| `audio` | an audio file | none | none |
| `audio_with_background` | an audio file | a photo | none |
| `photo` | a photo | none | 1 to 600 |

### `POST /scheduled-items`

Returns `201` with the `ScheduledItem`.

```jsonc
{
  "carepartner_id": 1,
  "media_id": 9,
  "background_photo_id": 4,      // optional, audio only
  "display_seconds": null,       // timed photos only
  "start_date": "2026-10-12",
  "start_time": "10:00",
  "repeat": "weekly",            // once | daily | weekly | monthly
  "end_date": null               // optional; not allowed for "once"
}
```

Rules the server enforces:

- `start_time` on a 15 minute step: :00, :15, :30 or :45 (`NOT_ON_15_MIN_STEP`). Offer only those times in the picker. We can change this if we want later.
- The item starts at or after wake time and finishes by bed time, counting its length (`OUTSIDE_AWAKE_HOURS`).
- Weekly repeats on the start date's weekday. Monthly repeats on the start date's day of the month and skips months without it, so an item on the 31st doesn't happen in November.

> **Overlap checking is the frontend's job.** Nothing lasts more than 10 minutes and items start on 15 minute steps, so two items overlap only if they start at the same time on the same date. Before saving, compare against the [calendar](#calendar) for that day and warn on a matching `time`.

### `GET /scheduled-items?carepartner_id={id}`

Each item once, as a rule, with its `skip_dates`. Use it for an "all scheduled items" list; use the calendar for anything date based.

### `GET /scheduled-items/{id}`

One item.

### `PUT /scheduled-items/{id}`

Replace an item; same body and rules as creating one (`carepartner_id` is ignored). Days already deleted stay deleted.

### `DELETE /scheduled-items/{id}?scope=series`

"Delete every time."

### `DELETE /scheduled-items/{id}?scope=occurrence&date=YYYY-MM-DD`

"Delete just this day." The date must be one the item happens on (`NOT_AN_OCCURRENCE` otherwise). For a `once` item this deletes the item.

## Calendar

### `GET /calendar?carepartner_id={id}&from=YYYY-MM-DD&to=YYYY-MM-DD`

Every dated occurrence from `from` to `to` (inclusive, at most 62 days), sorted by date then time, with deleted days already left out. Render it directly; **don't add a recurrence library**, since the server is the one source of truth for repeats.

```json
[{
  "scheduled_item_id": 7,
  "date": "2026-10-12",
  "time": "18:00",
  "repeat": "weekly",
  "shape": "audio_with_background",
  "media": { "id": 9, "kind": "audio", "display_name": "Morning hymn", "duration_seconds": 214, "url": "/media/9/file" },
  "background_photo": { "id": 4, "display_name": "Sarah", "url": "/media/4/file" },
  "display_seconds": null,
  "duration_seconds": 214,
  "outside_awake_hours": false
}]
```

`outside_awake_hours` is worked out from the current awake hours each time you ask. If the caregiver moves wake time later, existing items aren't edited or rejected; they're flagged here so the calendar can mark them.

For "delete just this day", pass the occurrence's `scheduled_item_id` and `date` to the delete endpoint.

### How to render it

- `spots` has exactly as many entries as the layout has spots, in spot order. `null` is an empty spot. Place each spot on screen by the convention under [presets](#get-screen-settingspresets): the widgets follow reading order.
- Hidden widgets are already left out.
- `data` by type: photo `{caption}`; weather the current conditions; sports `{team_name, result, opponent_team_name, team_score, opponent_score, ...}`; news `{articles}` (up to 3). Message and reminder widgets have `data: null`; everything is in `config`.
- If an outside service is down, that widget has `data: null` and `error: "UPSTREAM_UNAVAILABLE"`. Show a calm fallback for that widget only; the rest of the screen is fine. Weather and news need API keys on the server.
- `awake_hours.is_awake_now` says whether to show the screen or the screensaver. Use `wake` on the screensaver ("Wakes up at 7:00 AM").
- `schedule` covers today and tomorrow so playback keeps working past midnight. Trigger playback when the local time reaches an occurrence's `date` and `time`, as `carepartner/app/ScheduleContext.tsx` does today. Play photos for `duration_seconds`.
- A sports `result` of `upcoming` means the team hasn't played yet this season.

### Re-fetching

Poll `/screen` on a timer; there's no push yet. Every 5 minutes, as the tablet does now, is a sensible start, plus once right after midnight. Weather, sports and news are cached on the server for 10 minutes, so polling more often doesn't call the outside services more.

### Not decided yet

- The plain weather word ("Chilly"): use `temp` and `condition` until the temperature bands are agreed.
- The part of the day ("Afternoon"): work it out on the tablet for now.
- What the news widget shows long term.

## Playback

The tablet records each attempt to play something, so caregivers can later see what was played and how it went. Added in #346; since i332 a playback points at a **media item** (and, for scheduled plays, the scheduled item) instead of a module.

### `POST /playbacks`

Record that something is about to play. Returns `201` with the `Playback`.

```jsonc
{
  "carepartner_id": 1,
  "media_id": 9,
  "scheduled_item_id": 7,             // required when source is "scheduled"; leave out otherwise
  "source": "scheduled",              // scheduled | staff | tap
  "expires_at": "2026-10-12T15:15:00Z" // RFC 3339; the deadline to start playing
}
```

- For a scheduled play, take `media.id` and `scheduled_item_id` from the `/screen` schedule entry. For a tap or a staff-started play, send only `media_id`.
- The media must belong to the carepartner, and a scheduled item must belong to them and play that media. Otherwise `400`.
- `module_id` is no longer accepted (`400`). Unknown fields are rejected.

### `PATCH /playbacks/{id}/status`

Report progress: `{"carepartner_id": 1, "status": "started"}`. Statuses move forward only:

| From | Allowed next |
|---|---|
| `requested` | `acknowledged`, `stopped`, `failed`, `expired` |
| `acknowledged` | `started`, `stopped`, `failed`, `expired` |
| `started` | `finished`, `stopped`, `failed` |

Repeating the current status is harmless. Acknowledging or starting after `expires_at` records `expired` instead. An invalid move returns `409`.

### Staff play and stop

`POST /playbacks/play` with `{"carepartner_id": 1, "media_id": 9}` records a `staff` playback with a 30 second deadline and pushes it to the tablet over the WebSocket at `/realtime/tablet?carepartner_id=1`. `POST /playbacks/{id}/stop` with `{"carepartner_id": 1}` stops one. `module_id` is no longer accepted (`400`).

The tablet receives `{"type":"play","playback_id":12,"media_id":9,"expires_at":"..."}` (this field was `module_id`) and reports progress on the same socket with `{"type":"status","playback_id":12,"status":"acknowledged"}`. Look the media up with `GET /media/{id}`. A missed play command is resent when the tablet reconnects before it expires, unless the media was deleted in the meantime.

### Errors

These endpoints return `{"error": "..."}` without a `code`: `400` invalid input, `404` playback not found, `409` invalid status change, `500` otherwise. Deleting a media item keeps its playbacks and clears `media_id`; `media_kind` and `media_display_name` still say what played (the name as it was when it played). Deleting a scheduled item likewise keeps them and clears `scheduled_item_id`.

```ts
export type PlaybackSource = "scheduled" | "staff" | "tap";
export type PlaybackStatus = "requested" | "acknowledged" | "started" | "finished" | "stopped" | "failed" | "expired";
export interface Playback {
  id: number;
  carepartner_id: number;
  media_id: number | null;       // null once the media is deleted
  media_kind: "photo" | "video" | "audio";
  media_display_name: string;    // copied when the playback is created
  scheduled_item_id: number | null;
  source: PlaybackSource;
  status: PlaybackStatus;
  requested_at: string;          // RFC 3339
  acknowledged_at: string | null;
  started_at: string | null;
  ended_at: string | null;
  expires_at: string;
  rating: number | null;         // scale not decided yet
}
```

## Carepartner changes

- `auto_start` is gone. The server no longer returns it and ignores it if sent. `wake_time` in screen settings replaces it.
- `GET /users/carepartner/{id}` returns `{id, name, timezone}`.
- `POST /users/carepartner/create-carepartner` takes `{"name": "..."}` and returns `{"carepartner_id": 7}`; it also creates default screen settings.
- Device pairing (`/users/device-pairing/code`, `/verify`, `/status`) is unchanged.

## Migration checklist

### Caregiver web app

1. Add the fetch helper and types to a shared API module.
2. **Settings page first:** replace "Auto Start Time" with wake and bed time on `/screen-settings`. Today it silently drops what caregivers save.
3. Media library: one list with a kind filter, `usage` badges, durations, upload errors, and delete warnings.
4. Screen editor: take the layouts and spot counts from `/screen-settings/presets`, fill spots with `/screen-widgets`, list hidden widgets separately, swap with `/move`, take teams from `/widgets/sports/teams`, preview with `/screen`.
5. Calendar: render `/calendar`; schedule with quarter-hour times, the repeat options and the four shapes; check same-time overlap; offer "just this day" and "every time" deletes; mark `outside_awake_hours`.
6. Remove calls to the old media, widget, prompt, module and configuration endpoints, and the hardcoded team list.

### Carepartner tablet

1. Fetch `/screen` on a timer and render `spots` for each layout, with a fallback for `null` spots and `UPSTREAM_UNAVAILABLE` widgets.
2. Drive the screensaver from `awake_hours`; show `wake` instead of "Auto-Starts at".
3. Trigger playback from `schedule`, including audio with a background photo and timed photos.
4. Load media through `resolveApiUri(url)`.
5. Stop sending `AutoStart` from `pair.tsx` (harmless, but no longer used), and retire the `/configurations/day` agenda flow.
